# Известные ограничения и технические риски

Документ фиксирует текущую реализацию; перечисленные пункты не исправлялись в коде.

## 1. Нет явных зависимостей между DAG-ами

Все пять DAG-ов независимы и связаны только предполагаемым временем запуска. При задержке API или CRM downstream может стартовать на старых данных.

**Рекомендация:** Airflow Datasets, управляющий DAG, `ExternalTaskSensor` или объединение в один DAG.

## 2. Фактический cron противоречит требуемой цепочке

Matcher запускается в `01:15`, а обе витрины — в `22:20` и `22:40`. Это не соответствует описанному порядку расчета одного цикла.

## 3. Timezone не зафиксирован на уровне DAG

MacroCRM использует `Asia/Yekaterinburg` для fallback-даты, Яндекс — `data_interval_end`, а cron зависит от Airflow timezone. Возможен сдвиг расчетного дня.

## 4. Один full-load switch для двух источников

`macro_v2_full_load` управляет и MacroCRM, и Яндекс Директом. Название переменной не отражает второе назначение и увеличивает риск случайного тяжелого backfill.

## 5. Drop/recreate с `CASCADE`

`crm_yandex_leads_matched` и детальная витрина пересоздаются через drop. Риски:

```text
временная недоступность таблицы/view
удаление внешних зависимых views
неполное состояние при падении между drop и create
```

**Рекомендация:** staging table + transactional swap или materialized view refresh.

## 6. DDL внешних таблиц отсутствует

В комплекте нет миграций для:

```text
macro_estate_buys
macro_estate_buys_utm
yandex_campaigns
cabinets
project_cabinet_map
```

Нельзя воспроизвести окружение только из репозитория.

## 7. Разные определения сделок и выручки

Кампанийный слой считает любой `deal_id > 0` и всю `deal_sum`; детальный слой — только завершенные статусы. Это должно быть согласовано как metric contract.

## 8. Одна выбранная UTM-строка

Matcher выбирает одну «лучшую» UTM на заявку. Это не first-touch/last-touch модель с полным журналом и не multi-touch attribution.

## 9. Ограничение кандидатов Яндекса

Source из Яндекс-списка должен сочетаться с medium из рекламного списка, если нет динамических tokens. Часть заявок Яндекс.Недвижимости с другим medium может не попасть в matched-таблицу.

## 10. Legacy-проверка июля 2026

Matcher после пересборки всегда выполняет отдельный запрос `lead_date >= DATE '2026-07-01'`. Со временем лог станет объемнее и проверка потеряет operational-смысл.

**Рекомендация:** заменить на rolling window, например последние 14 дней.

## 11. Встроенная сверка агрегирована за весь период

Criterion DAG сравнивает суммы по кабинету без даты. Теоретически положительная ошибка одного дня может компенсировать отрицательную ошибку другого.

**Рекомендация:** сверять как минимум `date + cabinet_id`, а лучше `date + cabinet_id + campaign_id`.

## 12. Нет версионирования зависимостей и CI

В комплекте отсутствуют:

```text
Airflow constraints / lock file
requirements с версиями
unit tests
SQL tests
automated DAG import test
CI pipeline
```

## 13. Последовательная и потенциально тяжелая загрузка Яндекса

Аккаунты и дни обрабатываются последовательно, каждый день требует три API-отчета. Full load с начала 2026 года может выполняться долго и упираться в API limits.

## 14. Postgres upsert Яндекса идет построчно

`upsert_dataframe_to_postgres` выполняет `conn.execute` на каждую строку. На больших объемах это медленнее batch upsert/COPY.

## 15. `v_macro_traffic_sources_report` не входит в кодовый комплект

Старый README описывал эту view, но ни один из пяти переданных DAG-ов ее не создает, а отдельный SQL-файл не передан. В новой документации она не считается частью воспроизводимого core pipeline.

## 16. Формула `cost * 1.22` жестко зашита

View фиксирует коэффициент в SQL. При изменении бизнес-правила потребуется изменение кода и пересоздание view.
